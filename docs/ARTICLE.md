# 用 Verilator 驗證一個 FPGA 訂單簿：我量到的數字與踩到的坑

> 這是一篇技術紀錄，不是教學。所有數字都來自本 repo 的可重跑流程，
> 所有「失敗」都保留在版本歷史裡，因為失敗比成功有資訊量。

## 0. 緣起：延遲不是勝負關鍵

我原本在做台股當沖的策略研究。結論很早就出來了：**成本（手續費 + 證交稅 27.6 bps）
才是勝負關鍵，不是硬體速度。** 一個 10 ns 的訂單簿，接上券商 API 是 10~50 ms，
延遲優勢被吃掉三個數量級。

但我還是想回答一個工程問題：

> **在 FPGA 上做一個訂單簿核心，假設不用管券商 API，它的極限在哪？**

這個 repo 是那個問題的答案——不是產品。

## 1. v0.1 的範圍

刻意做小：價位聚合（level-indexed price ladder）、最佳買賣價、ADD/CANCEL/TRADE
的價位層級語意。**沒有**訂單個體、沒有 FIFO、沒有 queue position。

為什麼？因為這個版本的目的不是功能，是**把驗證流程走通並留下數字**。
功能可以之後加，方法論要先確立。

## 2. 驗證：三層，缺一不可

### 2.1 Python golden model

`model/book_model.py` 用 list 與任意精度整數重寫一次語意，產生刺激與期望值。
testbench 讀 `stim.txt` / `exp.txt`，逐筆比對 7 個欄位（bid/ask 的 valid、level、qty、全簿 checksum）。

- 222 筆命令（22 directed + 200 隨機）× 7 欄位 = **1,554 次比對**

**限制**：golden model 和 RTL 是同一個人寫的。共同誤解規格時，測試照樣全綠。

### 2.2 不變量

testbench 內建與 model 無關的檢查：`bid_valid` 必須等價於「深度非零」、
`best_*_qty` 必須等於該 level 的深度值、最佳買賣價之上/之下不得有非空價位。

這層抓的是「實作與 model 都沒想到」的結構性錯誤。

### 2.3 突變測試：證明測試有牙齒

`tools/mutate.py` 把 RTL 的關鍵字串改壞，看測試抓不抓得到。30 個 mutant：

```
mutants      : 30
killed       : 29
equivalent   : 1
survived     : 0
mutation score: 100.0%
```

但真正有價值的是**過程中存活的兩個 mutant**。

#### 故事一：移除 `cmd_valid` gate，測試全綠

把寫入條件 `else if (s1_valid)` 改成 `else`，測試照樣通過。

原因：testbench 每個 cycle 都送命令，**從來沒有「沒有命令」的 cycle**。
所以那個 gate 根本沒被執行過。

修法不是改 RTL，是補測試：每 5 步插入 2 個閒置週期，並檢查狀態不得改變。

#### 故事二：ask 側的 8-bit 截斷存活

把 ask 側的加法截斷成 8 bit，測試沒抓到——因為**ask 側從來沒測過大數量**。
directed corner case 補上「ask 側 65535 再加 2（回繞成 1）」之後才殺掉。

**這兩個故事的重點：突變測試抓到的不是 RTL 的 bug，是測試的洞。**

## 3. 時序：Fmax 不是延遲

| 版本 | 級數 | Fmax | 延遲 | 吞吐 |
|---|---|---|---|---|
| 單級 | 1 | 95.65 MHz | **10.45 ns** | **95.7 M/s** |
| 兩級 | 2 | 154.58 MHz | 12.94 ns | 77.3 M/s |
| 三級（算術再切） | 3 | 155.86 MHz | 19.25 ns | 51.9 M/s |

**頻率 +62%，但延遲與吞吐都變差。** 因為切管線時，每級邏輯只縮短了 1.6 倍，
級數卻變 2 倍。這是 pipeline 的經典陷阱。

三個 placement seed 的變異：95.82 / 91.75 / 93.43 MHz → 不是佈局運氣，是邏輯深度。

三級版本（把 16-bit 加減拆成兩個 8-bit 半）只多 0.8% 的頻率，卻多一拍延遲。
critical path 顯示：拆完之後，**邏輯只佔 3.1 ns，其餘 3.3 ns 是繞線**。
在 ECP5 上，這個結構的瓶頸已經從邏輯變成繞線。

## 4. bitmap 實驗：O(log N) 不是免費的

為了支援 1,024 級，試了 occupancy bitmap + 優先編碼。

| 版本 | Fmax | LUT4 |
|---|---|---|
| 線性掃描（64-way + 16-way 鏈） | 66.49 MHz | 4,490 |
| 樹狀（4→4→4） | 81.45 MHz | 4,510 |

**只快 22%，不是預期的 2 倍。** critical path 顯示瓶頸在「從 1,024 個 bit 挑出 word」
的寬 mux，不是掃描本身。

### BRAM 陷阱

把 1,024 × 16 的價位陣列改成 BRAM 時踩了一個坑：

```systemverilog
wire cur_q = bid_q[cmd_level];   // 非同步讀
```

read-modify-write 需要組合讀，**Yosys 因此無法推論 BRAM**，把 2×1,024×16 全拆成暫存器，
LUT 爆到 102k（122%），P&R 超過 20 分鐘跑不完。

正確做法是把命令處理拆成 S1（發讀）/ S2（算）/ S3（寫回）——也就是 SPEC 裡原本的管線。

## 5. 工具現實

- **Yosys + nextpnr**：免費、可腳本化，但沒有 retiming、沒有商用品質的時序優化。
- **Vivado**：安裝 50~100 GB，且 325T 可能需要付費授權。
- **Lattice Diamond**：免費、體積小，ECP5 的官方 STA 要用它。

所有 Fmax 都是 nextpnr 佈局後估計，誤差可能 10~20%。

## 6. 十條教訓

1. **Fmax 不是目標**，延遲（ns）與吞吐（events/s）才是。
2. 切管線會增加延遲；只有在「每級邏輯等比例縮短」時才划算。
3. 突變測試抓的是**測試的洞**，不是 RTL 的 bug。
4. 等值突變（equivalent mutant）必須排除，否則分數會誤導。
5. 合成分不出「架構問題」：加暫存器、改演算法，它都不會幫你。
6. 非同步讀會殺死 BRAM 推論。
7. 1,024 級的寬 mux 比你想的貴。
8. 大設計的 P&R 時間會摧毀迭代速度，先用小參數迭代。
9. golden model 與 RTL 同作者時，不變量與突變測試是必要的補充。
10. **先問「這要幹嘛」，再問「怎麼做更快」。**

## 7. 如果你也想做一個

- 從最小可驗證的東西開始（不要一開始就 1,024 級）
- 先寫 golden model，再寫 RTL
- 突變測試越早做越好，它會改寫你對「測試」的定義
- 量延遲，不要只量頻率
- 把失敗留下來：三級版本、bitmap 的 66 MHz、BRAM 的 122%——那些比成功更有說服力
