# 我把 Fmax 拉高了 62%，結果延遲變差了

## 一個反直覺的數字

先看這張表。同一個電路，只差在「切成幾級管線」：

| 版本 | 級數 | Fmax | 延遲 | 吞吐 |
|---|---|---|---|---|
| 單級 | 1 | 95.65 MHz | 10.45 ns | 95.7 M/s |
| 兩級 | 2 | 154.58 MHz | 12.94 ns | 77.3 M/s |
| 三級 | 3 | 155.86 MHz | 19.25 ns | 51.9 M/s |

頻率上升了 62%。但延遲和吞吐**都變差了**。

這是真的發生在我身上的事。我花了幾個小時把一個 FPGA 訂單簿切管線、量頻率、慶祝 Fmax 變高，然後坐下來算延遲，才發現自己一直在優化一個不是目標的數字。

這篇文章記錄那個過程，以及後面三個實驗踩到的坑。所有數字都可以在 GitHub 上重跑，沒有經過任何美化的「大約」。

## 我在做的東西

我原本在做台股當沖的策略研究。研究很快就有結論：**成本才是勝負關鍵，不是硬體速度。** 手續費加證交稅，一個來回就是 27.6 bps；而券商 API 的延遲是 10 到 50 毫秒。就算硬體快 100 倍，也追不回那三個數量級的差距。

但我還是想回答一個純工程問題：

> 如果不管券商 API，一個 FPGA 訂單簿核心的極限在哪？

於是我做了一個刻意很小的版本：價位聚合（price ladder）、最佳買賣價、以及 ADD／CANCEL／TRADE 在「價位層級」的語意。**沒有**訂單個體、**沒有**佇列、**沒有** queue position。

為什麼做小？因為這個版本的目的不是功能，是把「規格 → RTL → 對拍 → 突變測試 → 覆蓋率 → 時序」整條流程走完，並且留下可驗證的數字。

至於為什麼是 16 級而不是 1,024 級：因為 16 級的邏輯深度還能在這顆 40 奈米元件上跑出可用的頻率，而 1,024 級會讓「選出最佳價」這件事本身變成臨界路徑。先在最單純的規模把流程與數字建立起來，再往上放大，比一開始就做大的、然後什麼都量不出來要實際。

還有一個更現實的理由：合成與佈局的時間。16 級的設計，合成幾十秒、佈局一兩分鐘，一小時可以迭代十幾次。1,024 級的版本，光佈局就超過二十分鐘，迭代速度會直接崩掉。**在硬體設計裡，迭代速度本身就是一種資源。**

## 為什麼延遲比頻率重要

延遲的公式很簡單：

```
延遲 = 級數 × 週期
```

單級版本：1 ÷ 95.65 MHz = 10.45 ns。
兩級版本：2 ÷ 154.58 MHz = 12.94 ns。

頻率變高了，但每一級只把臨界路徑縮短了 1.6 倍，級數卻變成兩倍。所以總延遲反而變大。

這不是特例，是切管線的通則：**只有當「每一級縮短的比例」大於「級數增加的比例」時，切管線才會降低延遲。** 否則你只是拿延遲去換一個好看的頻率數字。

我又跑了三個不同的佈局種子：95.82、91.75、93.43 MHz。差距只有幾 MHz，證明問題出在邏輯深度，不是佈局運氣。

三級版本更值得說。我把 16 位元的加減法拆成兩個 8 位元半，想讓進位鏈變短。結果頻率只多了 0.8%，延遲卻多了 6 ns。看時序報告才發現：拆完之後，邏輯只佔 3.1 ns，**繞線佔 3.3 ns**。在這顆 40 奈米元件上，瓶頸已經從邏輯變成線。

## 第二個實驗：O(log N) 不是免費的

為了支援 1,024 個價位，我試了「佔用位元圖 + 優先編碼」：每個價位一個 bit，用兩層樹找出最高與最低的非零位。

| 版本 | Fmax | LUT4 |
|---|---|---|
| 線性掃描（64 路 + 16 路串鏈） | 66.49 MHz | 4,490 |
| 樹狀（4-4-4） | 81.45 MHz | 4,510 |

只快了 22%，不是我預期的兩倍。時序報告顯示：新的瓶頸是「從 64 個 word 裡挑出一個」的寬 mux，不是掃描本身。

教科書說 bitmap 是 O(log N)，但它沒告訴你，那個 log N 的常數在真實元件上有多貴。

## 第三個實驗：非同步讀會殺死 BRAM

把 1,024 × 16 的價位數量陣列搬進 block RAM，聽起來很合理。我改了 `ram_style`，合成，然後得到 122% 的 LUT 使用率——放不進元件，佈局跑了 20 分鐘沒結束。

原因只有一行：

```systemverilog
wire cur_q = bid_q[cmd_level];  // 非同步讀，用於讀-改-寫
```

因為「讀-改-寫」需要組合邏輯讀取，合成器無法推論成 BRAM，只好把 32,768 個位元全部攤成正反器，再加上 1,024 選 1 的寫入解碼與讀取多工器。

修法不是改參數，是改架構：把命令處理拆成 S1（發出記憶體讀取）、S2（計算新值）、S3（寫回），這樣記憶體才有機會變成 BRAM。而這正是規格書從一開始就寫的管線。

**我繞了一圈，回到自己寫的 SPEC。**

## 驗證：突變測試抓到的兩個洞

這個專案裡，驗證比 RTL 有趣。三層防線：

1. **Python 參考模型**：用 list 和任意精度整數重寫一次語意，產生刺激與期望值，testbench 逐筆比對。222 筆命令 × 7 個欄位，共 1,554 次比對。
2. **不變量**：不依賴模型的結構檢查，例如「valid 必須等價於深度非零」。
3. **突變測試**：把 RTL 改壞，看測試抓不抓得到。30 個突變體，29 個被殺、1 個等值、0 個存活。

真正有價值的是**開發過程中存活的兩個**。

第一個：把寫入條件 `else if (s1_valid)` 改成 `else`，測試照樣全綠。因為 testbench 每個週期都送命令，**從來沒有「沒有命令」的週期**。那個條件根本沒被執行過。

第二個：把 ask 側的加法截斷成 8 位元，測試也沒抓到。因為 ask 側從來沒測過大數量。補上「65535 再加 2，回繞成 1」這個案例之後才殺掉。

兩次存活，指出的都不是 RTL 的 bug，而是**測試的洞**。

這就是突變測試的價值：它是唯一能回答「我的測試到底有沒有牙齒」的方法。覆蓋率告訴你「哪一行被執行了」，但它不會告訴你「執行了卻沒檢查」。

不過這套方法有一個必須承認的限制：**參考模型和 RTL 是同一個人寫的。** 如果作者對規格有共同的誤解，模型會「正確地」重現那個誤解，測試照樣全綠。這也是為什麼除了對拍之外，還要加上不變量與突變測試——它們各自抓不同的錯誤類型，沒有任何一層能單獨保證正確。

## 工具與現實

| 工具 | 狀況 |
|---|---|
| Yosys + nextpnr | 免費、可腳本化、能算出真實 Fmax；但沒有 retiming，時序優化比商用工具弱 |
| Vivado | 安裝 50~100 GB，325T 可能需要付費授權 |
| Lattice Diamond | 免費、體積小，ECP5 的官方時序簽核要用它 |

所有數字都是 nextpnr 佈局後的估計，不是簽核值，誤差可能 10~20%。這件事我在文章和 repo 裡都標清楚了，因為被問到「這數字可信嗎」的時候，誠實比漂亮重要。

為什麼不直接換成 Kintex-7 加 Vivado？因為那需要几十 GB 的安裝空間，而且 325T 可能還要付費授權。以一個純粹想驗證流程的專案來說，先用手上免費、可腳本化的工具鏈把數字量出來，比先花兩天裝工具、再開始設計要有效率。等架構穩定、真的需要簽核數字時，再換工具也不遲。

## 五條教訓

1. **Fmax 不是目標。** 延遲（奈秒）和吞吐（每秒事件數）才是。頻率只是手段。
2. **切管線會增加延遲**，除非每一級都等比例縮短。
3. **突變測試抓的是測試的洞**，不是 RTL 的 bug。
4. **合成救不了架構。** 它不會幫你加暫存器，也不會幫你換演算法。
5. **非同步讀會殺死 BRAM 推論**，而且錯誤訊息不會告訴你原因，只會給你 122% 的 LUT。

## 這個專案不是什麼

它不是交易系統。沒有行情解析、沒有風控、沒有下單、沒有佇列。它是一個 block，而且是刻意做小的那個 block。

它也不是產品。它存在的理由是：把驗證流程走通、把失敗留下來、把數字量出來。

## 給想入門的人

- 從最小可驗證的東西開始，不要一開始就 1,024 級。
- 先寫參考模型，再寫 RTL。
- 突變測試越早做越好，它會改寫你對「測試」的定義。
- 量延遲，不要只量頻率。
- **把失敗留下來。** 三級版本、66 MHz 的 bitmap、122% 的 LUT——那些比成功更有說服力。
